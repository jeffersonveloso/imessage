# Login via HTTP REST API

This document explains how to authenticate with the iMessage bridge using the
HTTP REST API. The login is a **multi-step flow** — the API guides you through
each step, telling you exactly which fields to submit.

## Prerequisites

- The HTTP API must be enabled in `config.yaml`:
  ```yaml
  network:
      api:
          enabled: true
          listen: "0.0.0.0:8080"
          api_key: "your-api-key-here"
  ```
- All requests require the `Authorization: Bearer <api_key>` header.
- For the **External Key** flow, you need a hardware key extracted from a Mac
  (see [Extract the Hardware Key](#1-extract-the-hardware-key)).

## Overview

```
GET  /api/v1/login/flows  →  List available login methods
POST /api/v1/login/start  →  Choose a method, receive session_id + first step
POST /api/v1/login/step   →  Submit data for current step, receive next step
POST /api/v1/login/step   →  (repeat until complete)
```

Each response tells you:
- `session_id` — your session identifier (same throughout the flow)
- `step_id` — which step you're on
- `instructions` — human-readable explanation of what to do
- `fields` — array of fields to fill in for the next `/login/step` call
- `complete` — present only on the final step, indicating success

## Available Login Flows

| Flow ID          | Name                     | Platform | Description                                     |
|------------------|--------------------------|----------|-------------------------------------------------|
| `external-key`   | Apple ID (External Key)  | Any      | Uses a hardware key extracted from a Mac.        |
| `apple-id`       | Apple ID                 | macOS    | Uses the local Mac's hardware directly (no key). |

The **External Key** flow is the primary method for Docker and Linux deployments.

## Endpoints

### `GET /api/v1/login/flows`

Returns the list of available login flows.

**Response:**
```json
{
  "flows": [
    {
      "id": "external-key",
      "name": "Apple ID (External Key)",
      "description": "Log in using a hardware key extracted from a Mac. Works on any platform."
    }
  ]
}
```

### `POST /api/v1/login/start`

Starts a new login session. Returns a `session_id` and the first step.

**Request body:**
```json
{
  "flow": "external-key"
}
```

### `POST /api/v1/login/step`

Submits user input for the current step. Returns the next step or completion.

**Request body:**
```json
{
  "session_id": "abc123...",
  "input": {
    "field_id": "value"
  }
}
```

The keys in `input` correspond to the `id` of each field in the previous
response's `fields` array.

## Step-by-Step: External Key Flow

### 1. Extract the Hardware Key

On the Mac whose identity you want to use, run:

```bash
cd tools/extract-key
go build -o extract-key .
./extract-key
```

> **Important:** The key must be generated by this project's `extract-key` tool.
> Third-party apps (like "Mac Hardware Info" from the App Store) produce a
> different format that is not compatible.

The tool prints a **base64-encoded** string to stdout. This is your hardware key.
Save it — you'll paste it in step 4.

**Apple Silicon Macs** require the NAC relay running on the same Mac:

```bash
# Terminal 1 — start the relay (keep running)
go run tools/nac-relay/main.go

# Terminal 2 — extract with relay
cd tools/extract-key
go build -o extract-key .
./extract-key -relay https://localhost:5001/validation-data
```

### 2. List Login Flows

```bash
curl -s http://localhost:8080/api/v1/login/flows \
  -H "Authorization: Bearer YOUR_API_KEY" | jq .
```

**Response:**
```json
{
  "flows": [
    {
      "id": "external-key",
      "name": "Apple ID (External Key)",
      "description": "Log in using a hardware key extracted from a Mac. Works on any platform."
    }
  ]
}
```

### 3. Start Login

```bash
curl -s -X POST http://localhost:8080/api/v1/login/start \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"flow": "external-key"}' | jq .
```

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.externalkey",
  "instructions": "Enter your hardware key (base64-encoded JSON)...",
  "fields": [
    {
      "id": "hardware_key",
      "name": "Hardware Key (base64)",
      "type": "password"
    }
  ]
}
```

Save the `session_id` — you'll use it in all subsequent steps.

### 4. Submit Hardware Key

Paste the base64 string from `extract-key` as the value of `hardware_key`:

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "hardware_key": "eyJpbm5lciI6eyJwcm9kdWN0X25hbWUiOi..."
    }
  }' | jq .
```

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.appleid",
  "instructions": "Enter your Apple ID credentials...",
  "fields": [
    { "id": "username", "name": "Apple ID", "type": "email" },
    { "id": "password", "name": "Password", "type": "password" }
  ]
}
```

### 5. Submit Apple ID Credentials

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "username": "you@icloud.com",
      "password": "your-apple-id-password"
    }
  }' | jq .
```

**Response (if 2FA is required):**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.2fa",
  "instructions": "Enter your Apple ID verification code...",
  "fields": [
    { "id": "code", "name": "2FA Code" }
  ]
}
```

If 2FA is not enabled on the account, this step is skipped and the response
will be the device selection or handle selection step directly.

### 6. Submit 2FA Code

A push notification should appear on your trusted Apple devices. If it doesn't,
generate a code manually:

- **iPhone/iPad:** Settings → [Your Name] → Sign-In & Security → Two-Factor Authentication → **Get Verification Code**
- **Mac:** System Settings → [Your Name] → Sign-In & Security → Two-Factor Authentication → **Get Verification Code**

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "code": "123456"
    }
  }' | jq .
```

### 7. Select Device (CloudKit only)

> This step only appears when `cloudkit_backfill: true` is set in the config
> AND multiple Apple devices are found on the account.
> With `cloudkit_backfill: false` (default), this step is skipped.

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.select_device",
  "instructions": "Multiple Apple devices were found...",
  "fields": [
    {
      "id": "device",
      "name": "Device",
      "type": "select",
      "options": ["John's iPhone (iPhone15,2)", "John's MacBook Pro (Mac14,10)"]
    }
  ]
}
```

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "device": "John'\''s iPhone (iPhone15,2)"
    }
  }' | jq .
```

### 8. Enter Device Passcode (CloudKit only)

> Only appears when `cloudkit_backfill: true`. This is the PIN/password used to
> unlock the selected device — needed to join the iCloud Keychain trust circle.

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.device_passcode",
  "instructions": "Enter the passcode for John's iPhone (iPhone15,2)...",
  "fields": [
    { "id": "passcode", "name": "Device Passcode", "type": "password" }
  ]
}
```

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "passcode": "123456"
    }
  }' | jq .
```

### 9. Select Handle

Choose the identity for outgoing messages — what recipients will see your
messages "from".

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "fi.mau.imessage.login.select_handle",
  "instructions": "Choose which identity to use for outgoing iMessages...",
  "fields": [
    {
      "id": "handle",
      "name": "Send messages as",
      "type": "select",
      "options": ["tel:+15551234567", "mailto:you@icloud.com"]
    }
  ]
}
```

```bash
curl -s -X POST http://localhost:8080/api/v1/login/step \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "a1b2c3d4e5f6...",
    "input": {
      "handle": "tel:+15551234567"
    }
  }' | jq .
```

### 10. Login Complete

**Response:**
```json
{
  "session_id": "a1b2c3d4e5f6...",
  "step_id": "complete",
  "complete": {
    "login_id": "imessage:tel:+15551234567",
    "message": "Successfully logged in to iMessage. Bridge is starting."
  }
}
```

The bridge is now connected. You can verify with:

```bash
curl -s http://localhost:8080/api/v1/status \
  -H "Authorization: Bearer YOUR_API_KEY" | jq .
```

## Step-by-Step: Apple ID Flow (macOS only)

This flow is only available when the bridge is running directly on macOS.
It uses the Mac's local hardware identifiers automatically — no `extract-key`
needed.

The steps are the same as the External Key flow, except **step 4 (hardware key)
is skipped**. The flow starts directly at the Apple ID credentials step:

```
POST /login/start {"flow": "apple-id"}
  → step: Apple ID + Password
POST /login/step  {"input": {"username": "...", "password": "..."}}
  → step: 2FA Code
POST /login/step  {"input": {"code": "123456"}}
  → step: Select Device (if cloudkit_backfill)
  → step: Device Passcode (if cloudkit_backfill)
  → step: Select Handle
POST /login/step  {"input": {"handle": "tel:+15551234567"}}
  → complete
```

## How to Read Responses

Every response from `/login/start` and `/login/step` has this structure:

```json
{
  "session_id": "string",
  "step_id": "string",
  "instructions": "string (optional)",
  "fields": [ ... ] ,
  "complete": { ... }
}
```

| Field          | Description                                                                 |
|----------------|-----------------------------------------------------------------------------|
| `session_id`   | Your session ID. Pass it in every `/login/step` call.                       |
| `step_id`      | Identifies the current step. `"complete"` means login is done.              |
| `instructions` | Human-readable text explaining what to do.                                  |
| `fields`       | Array of fields to fill in. Each has `id`, `name`, `type`, and `options`.   |
| `complete`     | Present only on the final step. Contains `login_id` and `message`.          |

**Field types:**

| Type       | Description                                      |
|------------|--------------------------------------------------|
| `email`    | Email address (Apple ID).                        |
| `password` | Sensitive text (password, key, passcode).         |
| `select`   | Choose one from `options` array.                 |
| (empty)    | Free-text input (e.g., 2FA code).                |

**Rule:** Look at `fields[].id` in the response → use those as keys in the
next request's `input` object.

## Disconnecting (Logout)

To disconnect the active iMessage session:

```bash
curl -s -X POST http://localhost:8080/api/v1/logout \
  -H "Authorization: Bearer YOUR_API_KEY" | jq .
```

**Response:**
```json
{
  "status": "disconnected"
}
```

After disconnecting:
- The bridge stops sending and receiving messages.
- Webhook consumers receive a `disconnected` event.
- `GET /api/v1/status` will return `{"connected": false}`.
- To reconnect, go through the login flow again (`POST /login/start`).

If no session is active, the endpoint returns `503`:
```json
{
  "error": "no active session to disconnect",
  "code": "NOT_CONNECTED"
}
```

## Error Handling

| HTTP Status | Code                | Meaning                                     |
|-------------|---------------------|---------------------------------------------|
| 400         | `INVALID_REQUEST`   | Missing or invalid field in the request.     |
| 401         | `UNAUTHORIZED`      | Invalid or missing API key.                  |
| 404         | `SESSION_NOT_FOUND` | Session expired or invalid `session_id`.     |
| 500         | `LOGIN_FAILED`      | Login step failed (invalid credentials, etc).|
| 503         | `LOGIN_UNAVAILABLE` | Login provider not configured.               |

Error response format:
```json
{
  "error": "2FA verification failed — invalid code",
  "code": "LOGIN_STEP_FAILED"
}
```

## Session Expiration

- Login sessions expire after **10 minutes** of inactivity.
- If your session expires, start over with `POST /login/start`.
- Expired sessions return `404 SESSION_NOT_FOUND`.
- Only one login session is active per `session_id`. Completed sessions are
  removed automatically.
